### 4.2 해금 보상이 사용으로 이어지지 않음

현재 모험 준비로 가는 진입점은 새 게임 흐름이며, 저장이 있으면 초기화 후 진입한다. 도감의 친구 카드는 읽기용이고 설정에 동료 변경 기능이 없다. 따라서 얻은 루카·드래곤·다람쥐를 기존 진행을 유지하며 고를 수 있는 사용자 경로가 없다.

코드 근거: `src/game/ui/screens/HomeScreen.ts:66,68`, `SetupScreen.ts:111,118,136`, `src/game/ui/ModalController.ts:102,279`, `src/game/systems/ScoreSystem.ts:79`. 해금 후 재장착 실패를 끝까지 실기기에서 실행한 결과가 아니라, 전체 진입점과 저장 초기화 흐름을 확인한 판정이다.

계획: 지도/도감의 ‘함께할 친구 변경’, 획득 결과의 ‘함께하기’를 같은 선택 기능으로 연결한다. 변경 전후 별·진행·기록이 보존되고 새로고침 후에도 선택이 남아야 한다.

### 4.3 휴식 시간이 타수에 포함됨

통제된 시간 검사에서 1초 동안 `학교` 입력은 300타/분이었다. 120초 일시정지 후 1초를 더 입력하면 실제 입력 시간은 2초지만 분모가 122초가 되어 약 4.918타/분으로 떨어졌다.

근거: `src/game/systems/DailySystem.ts:96`, `TypingStats.ts:42,66`, `src/game/ui/screens/BattleScreen.ts:370`. 표시 시간·실제 입력 시간·미션 제한 시간을 구분하고, 휴식·백그라운드·준비 대기 포함 여부를 모드별 규약으로 정의할 필요가 있다.

### 4.4 손상 저장과 저장 실패

- JSON 문법 오류, JSON `null`, 구버전 누락 필드는 기본값 복구가 동작했다.
- JSON은 유효하지만 `progress.stageStars:null`, `clearedStages:null`인 저장은 얕은 병합을 통과했다. 홈에서 `Object.values` 예외가 발생해 버튼이 표시되지 않았다.
- 저장 용량 초과를 주입하면 설정 UI는 바뀌지만 실제 저장은 되지 않고 학생에게 안내가 없다.
- 초기화 취소는 데이터를 보존하고, 확인 후 초기화는 동작했다. 이름 직접 입력 제거와 기기 내부 저장도 장점이다. 조사한 실행 흐름에서 외부 전송은 관측하지 않았다. 이를 모든 환경의 보안 보증으로 확대하지 않는다.

근거: `src/game/systems/SaveSystem.ts:25–39,85–86`, `src/game/ui/screens/HomeScreen.ts:35`.

### 4.5 오프라인 안내와 실제 동작 차이

온라인 홈 방문 → 서비스워커 준비 → 온라인 재방문 → 오프라인 홈은 동작했다. 그 상태로 새 게임·설정·이야기를 통과해 아직 방문하지 않은 S1에 들어가면 배경/몬스터가 로드되지 않았고 `Cannot read properties of undefined (reading 'duration')` 오류로 전투가 정지했다.

현재 교사용 안내의 ‘한 번 열어 두면 인터넷 없이도 동작’은 이 조건에서 성립하지 않는다. `vite.config.ts:31–37`의 지역 자산 캐시 범위와 `src/game/scenes/StageIntroScene.ts:49–50`의 로딩 실패 처리, 안내 문구를 함께 정리해야 한다.

## 6. 전문적인 디자인으로 바꿀 방향

### 6.1 세계관과 화면 위계

방향은 **픽셀 판타지 모험책**이다. 기존 지역 배경과 캐릭터를 기준으로 패널 재질·모서리·선 두께·아이콘·색 역할을 통일한다. 진한 남색은 화면 바탕, 밝은 종이색은 읽기 영역, 초록은 주 행동, 금색은 성취, 하늘색은 정보, 산호색은 수정 피드백으로 제한해 활용한다. 정확한 색상 값은 구현 단계에서 대비를 측정해 결정한다.

현재 초보 제작 느낌을 만드는 주요 원인은 카드 넘침, 균일하지 않은 크기와 여백, 많은 지표의 동등한 강조, 상세한 픽셀 배경 위에 놓인 큰 평면 도형, 이야기 이미지와 선택 캐릭터의 정체성 차이다. 장면별 장식을 늘리는 것보다 공통 규격과 정보의 우선순위를 먼저 정한다.

스토리·플레이·도감·포스터·완주 화면의 캐릭터 표를 만든다. 고정된 대표 캐릭터를 보여 주는 영상과 사용자가 선택한 캐릭터를 혼동시키지 않도록 표현 방식을 정한다. 자산 재생성이 필요하면 그 범위와 목적을 이 표에서 먼저 확정한다.

### 6.3 실제 화면에서 측정한 문제

- 1280×720의 준비 화면에서 패널 오른쪽은 약 x=813, 마지막 친구 카드 오른쪽은 약 x=950이었다. 약 137px가 패널 밖으로 나왔다. 1024×768에서도 같은 형태의 넘침이 보였다.
- 1024×768에서 이름 약 11.7px, 일부 설명·섹션 제목 약 12.8px, 미리보기 설명 약 9.6px였다. 준비 완료 버튼은 높이 약 42px, 뒤로 버튼은 약 34px였다. 타이핑 목표 글자 자체는 더 크므로 화면의 모든 글자가 작다고 일반화하지 않는다.
- 결과 본문의 `clientWidth=888`, `scrollWidth=898`로 가로 스크롤이 발생했다. S3와 S4 결과에서 확인했다.
- 준비 화면의 캐릭터 카드는 키보드 포커스를 받아도 Enter/Space로 선택되지 않았다.
- 이야기 첫 줄이 표시될 때 최소 높이가 큰 종이 패널에 빈 공간이 남았다. 이야기 전체 텍스트가 항상 짧다는 의미는 아니다.

관련 위치: `src/game/Game.ts`의 고정 1920 기준 UI 스케일, `src/styles/screens.css:149,157,974`, `src/styles/components.css:633`, `src/game/ui/screens/SetupScreen.ts`.

태블릿에서는 본문 최소 16px, 주요 안내 18px 이상을 설계 목표로 삼고, 전자칠판에서는 본문 20px 이상을 목표로 삼는다. 화면 전체를 축소해 맞추는 방식에서 역할별 최소 크기를 갖는 반응형 배치로 전환한다. 48px 터치는 이 프로젝트의 학생 사용성 목표다. WCAG 2.2 AA의 최소 타깃 규정은 기본 24×24 CSS px 및 예외 조건이므로 48px를 법정·WCAG 필수값으로 표현하지 않는다. [W3C 타깃 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## 7. 성능·미디어·교실 준비

### 7.1 현재 실측

Production preview, Chrome **152.0.7977.83**, 1280×800, CPU 제한 없음. 조건별 **단회** 측정이다. 콜드는 새 브라우저 컨텍스트, 캐시는 서비스워커 준비 후 같은 컨텍스트다. 실제 배포 서버나 학교 평균 성능으로 해석하지 않는다.

| 조건 | 홈 조작 가능까지 | 홈 도달 시 페이지 전송량 |
|---|---:|---:|
| 로컬 무제한 · 콜드 | 4.636초 | 7,479,126B |
| 로컬 무제한 · 캐시 | 3.783초 | 0B |
| 다운로드 10Mbps / 업로드 2Mbps / 지연 80ms · 콜드 | 10.690초 | 7,538,303B |
| 같은 제한 · 캐시 | 1.816초 | 0B |

전송량은 홈 도달 시점의 NavigationTiming + 페이지 ResourceTiming `transferSize` 합계다. 진행 중 요청·서비스워커 자체 백그라운드 요청 전체를 포함하지 않는다. 캐시의 0B 역시 인터넷 통신 전체가 0이라는 뜻이 아니다. HTML은 gzip이고, 앱 JS 75,086B/원본 256,634B, Phaser JS 339,838B/원본 1,481,766B 등 브라우저 응답에서 압축이 확인됐다. 압축 부재를 원인으로 추정하지 않는다. P95·평균·CPU 병목은 아직 측정하지 않았다.

자산 현황: public 401개·95.40MB, dist 409개·97.35MB. 완주 영상 35.86MB, 포스터 2.72MB, 미사용 OG 샘플 5개 19.09MB, BGM 8개 15.17MB, 글꼴 211개 4.39MB. 해시가 같은 완전 중복 파일은 발견되지 않았다. 디스크 용량 전체와 첫 화면 전송량은 다른 수치다.

### 7.2 개선 목표

1. 홈에서 바로 쓰는 자산만 우선 요청하고, 모험 준비·다음 지역·영상은 사용 시점에 맞춰 받는다. 진행률과 재시도를 제공한다.
2. 기존 완주 영상을 **로컬에서 웹용으로 압축하고 faststart 적용**한다. 3~6MB를 1차 용량 목표로 두되 픽셀 윤곽·문자·색·동작을 비교해 최종 결정한다. 새 영상 생성이나 힉스필드 재업로드 없이 가능한 작업이다.
3. 첫 화면 필수 전송량 1.5MB 이하, 지정 기기·10Mbps 조건의 홈 조작 가능 P95 3초 이하를 11점 목표로 둔다. 구현 후 충분한 반복 측정으로 검증한다.
4. 에셋 목록으로 참조·원본·웹용·사용권·지역별 다운로드 크기를 관리한다. 미사용 샘플은 기록을 남겨 보관하고 납품 산출물에서 제외한다.
5. 교사가 온라인일 때 ‘수업 준비 다운로드’를 실행한다. 필수 게임 자산의 완전성을 확인한 후 준비 완료를 표시한다. 선택 영상까지 오프라인 재생하려면 그 포함 여부와 용량도 안내한다. 영상이 없어도 대체 화면과 인증서는 동작해야 한다.
6. 새 버전 캐시가 일부만 받아지거나 연결이 끊긴 상태를 시험한다. 오래된 코드와 새 데이터가 섞여 게임을 멈추게 하지 않는다.

오디오에는 전역 매니저가 이미 있다. 다만 음소거 시 현재 BGM 이름을 지워 같은 장면에서 다시 켤 때 재개하지 못할 가능성이 코드에서 보인다(`AudioManager.ts:223` 이후). 실제 청취 검증 후 확정한다. 현재 완주 영상은 오디오 스트림이 없으므로 무음 영상 위에 의도한 한 개 BGM이 흐르는 상황을 이중 소리 충돌로 판정하지 않는다.

## 8. 구현 시 실행할 작업 묶음과 완료 기준

아래는 **아직 실행하지 않은 계획**이다. 우선순위 P0는 납품 전에 반드시 해결할 항목이다.

| G. 콘텐츠·인수인계 정리 | **P1, 최종 규칙 확정 후** | 성취기준 매핑, 도움말과 실제 규칙 동기화, 콘텐츠 검증, 저작권·버전·빌드·운영·복구·납품 파일 목록 | 깨끗한 환경에서 설치/검사/빌드 재현, 다른 개발자 콘텐츠 추가, 모든 자산 권리 근거와 납품 파일 확인 |

병렬 작업은 충돌을 줄이도록 파일 소유권을 나눈다. 교육 규칙과 결과 데이터 구조는 먼저 합의하고, 기능 담당이 systems/types/save를, 디자인 담당이 공통 토큰·화면 배치를, 자산 담당이 media/cache/build를 맡는다. 같은 결과 화면을 여러 담당이 동시에 고치지 않고 통합 시점을 정한다.

일정은 현재 범위 기준 **개발·디자인 약 10~15 작업일 + 학생 관찰·지연 확인 기간**을 1차 추정으로 둔다. 외부 검수 응답·사용권 증빙·새 자산 제작 범위에 따라 달라진다. 첫 단계 종료 조건은 ‘새 화면 완성’이 아니라 P0 우회·정지·저장 실패 재검증 통과다.

## 9. 교육효과와 재미의 검증 계획

현재 교사용 안내에 적힌 초등 3~6학년·물리 키보드 사용을 우선 검증 범위로 삼는다. 저학년 전체까지 효과를 입증한 것으로 표현하지 않는다.

| 검증 | 제안 방법 | 확인할 결과 |
|---|---|---|
| 시작 이해 | 타자 초보/보통/숙련을 포함한 학생 6~9명 정도로 형성 평가. 교사가 먼저 설명하지 않고 첫 행동 관찰 | 주 행동 발견까지 시간, 도움 요청, 잘못 누른 버튼, 왜 타이핑하는지 이해 |
| 재미·실패 경험 | 15~20분 관찰, 성공/실패 직후 짧은 질문, 자발적 재도전 기록 | 이펙트 선호 외에 재도전 이유·친구 보상 이해·실패 후 복귀 확인 |
| 기능 학습 | 같은 난이도의 처음 보는 낱말·문장으로 사전/사후 검사 | 정확도·정답 타수·수정 성공을 분리. 이미 외운 출제 문항의 향상과 구분 |
| 전이·유지 | 게임 연출이 없는 새 문장 입력 및 3~7일 뒤 다른 동등 문항 확인 | 한 판의 속도 상승을 넘어 오류 패턴 감소가 새 사례에서도 유지되는지 |
| 교실 사용 | 교사 2명 내외로 수업 준비·실기기·공유 기기 초기화·소리·중단·오프라인 검토 | 준비 실패·학생 멈춤·기록 손실·수업 개입 횟수, 안내만으로 운영 가능한지 |

참여 규모는 초기 사용성 개선을 위한 제안이며 통계적 효과 입증에 충분하다고 주장하지 않는다. ‘학생 90%가 설명 없이 시작’ 등은 향후 검수 목표 후보이지 현재 달성치가 아니다. 정식 효과 홍보가 필요하면 표본·비교 조건·동의 절차를 별도로 설계한다. 아동 실명이나 서버 기반 행동 수집을 이 계획의 전제로 두지 않는다.

정확도와 속도는 따로 본다. 도움을 쓴 학생과 쓰지 않은 학생을 단순 서열화하지 않고 같은 학생의 비슷한 난이도 수행을 비교한다. 게임에 제시된 글을 따라 치는 것은 그 자체로 인출 연습이 아니다. 짧은 수정 피드백·간격을 둔 재확인·새 사례 적용을 설계 근거로 참고하되 이 게임의 효과가 이미 검증됐다고 표현하지 않는다. [IES 학습·학습활동 구성 가이드](https://ies.ed.gov/ncee/wwc/Docs/PracticeGuide/20072004.pdf)

교육과정은 교육부 고시의 국어·실과 원문과 실제 콘텐츠를 대응해야 한다. 이번 조사에서는 고시와 별책 안내를 확인했지만 첨부 원문의 개별 성취기준까지 완전 대조하지 못했다. 따라서 성취기준 코드를 임의로 넣지 않는다. [교육부 2022 개정 교육과정 고시](https://www.moe.go.kr/boardCnts/viewRenew.do?boardID=141&boardSeq=93458&lev=0&searchTyp=)

움직임 감소 설정은 CSS뿐 아니라 Phaser 흔들림·입자·축하 영상에도 의도대로 적용되는지 확인한다. W3C의 상호작용 애니메이션 제어는 AAA 항목이며, 이를 AA 의무라고 잘못 설명하지 않는다. [W3C 상호작용 애니메이션](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

## 10. 납품 재개 조건과 최종 산출물

**납품 재개 조건:** P0 결함 재현 불가, 빌드·기존 검사·신규 의미 검증 통과, 저장/오프라인 복구 확인, 대상 화면 크기와 실제 기기 점검, 권리·버전·가이드 확인. 전체 점수가 높아져도 핵심 학습·데이터·진행 불가 FAIL 하나가 남으면 보류한다.

업체에 전달할 묶음은 릴리스 산출물, 재현 가능한 소스·잠금 파일, 에셋 출처/권리/생성 이력, 실행·수정·복구 안내, 학생·교사용 안내, 21항목 재검수표, 제작기·고도화 변경 기록이다. BGM의 생성 당시 이용 등급 등 사용권 근거는 아직 확인되지 않았으므로 증빙 대상으로 남긴다. 무단 이용이라고 단정하지 않는다. 새 완주 영상 기록을 중앙 크레딧에 연결하고 글꼴 라이선스 원문도 정리한다.

현재 앱 표시 버전 v0.2.0과 package 0.1.0, README 검사 6종과 실제 7종, 제작자 TODO, 현재 규칙과 설명 차이를 정리해야 한다. `output/`의 원본·도구 파일은 납품 대상으로 자동 포함하지 않고 목록으로 구분한다. 현재 작업에서 삭제하거나 옮기지 않았다.

실제 배포 주소의 캐시·재방문·직접 접근·메타데이터·영상·저장·기기별 동작은 배포 후보가 정해진 뒤 확인한다. 배포 주소가 바뀌면 localStorage 기록이 자동 이전되지 않는 점도 업체 안내에 명시해야 한다.
